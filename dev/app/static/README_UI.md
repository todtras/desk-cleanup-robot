# 사용자 화면 (B 담당)

```
index.html      메인 — 실시간 화면 2개, 상태, 진행, 버튼 6개, 알림
settings.html   설정 — 정리할 물건, 속도, 다시 시도 횟수, 수거함 안내
style.css       공통 스타일 (색·간격·버튼 크기를 여기서만 정한다)
app.js          공통 동작 (상태 확인, 버튼 규칙, 인식 박스, 연결 끊김 처리)
```

실행은 가이드와 같다. `dev` 폴더에서:

```bash
.venv-ui/bin/python -m uvicorn app.server:app --host 0.0.0.0 --port 8000 --timeout-graceful-shutdown 1
```

이번 UX 검증에서는 다른 작업의 8000번 서버를 건드리지 않고 `127.0.0.1:8001`만 사용했다.
시나리오별 조작·발견·수정 후 결과는 [UX_REVIEW.md](UX_REVIEW.md)에 기록했다.

서버와는 `/api/...` 와 `/video/...` 로만 이야기한다. `cleaner.py` 안을 직접 들여다보지
않으므로, 9주차에 `FakeCleaner`가 `RealCleaner`로 바뀌어도 화면은 그대로 돌아간다.

## 이렇게 만든 이유

**버튼 켜고 끄기는 표를 그대로 코드로 옮겼다.** `app.js`의 `STATES`가 가이드 2-3 표다.
상태마다 쓸 수 있는 버튼만 적어 두고 나머지는 자동으로 꺼진다. 표가 바뀌면 그 한 곳만 고치면 된다.
비상정지 상태에서는 비상정지 버튼이 꺼지고(이미 멈춰 있다), 물건 놓기와 정리 시작만 켜진다.

**인식 박스는 영상 위에 HTML로 얹는다.** 서버가 영상에 박스를 구워 넣으면 OpenCV가 한글
폰트가 없어서 `pen 0.82`처럼 영어로만 나온다. `/api/status`의 `detected` 좌표를 받아
화면에서 직접 그리면 `펜 82%`로 보여줄 수 있고, 휴대폰이든 노트북이든 영상 크기가 달라져도
%로 계산하니 박스가 따라간다.

**박스는 물건이 아직 책상에 있을 때만 그린다**(`detecting`, `picking`).
들고 옮기는 중이거나 멈춘 뒤에도 박스를 띄우면, 이미 없는 자리를 가리키게 된다.

**확인 창은 `confirm()` 대신 직접 만들었다.** 휴대폰에서 기본 확인 창은 작고 글씨를 바꿀 수
없다. 물건 놓기처럼 "왜 확인을 받는지"를 설명해야 하는 자리에는 맞지 않는다.

**비상정지는 화면 아래에 고정했다.** 어디까지 스크롤했든 항상 보이고, 손가락으로 누르기
좋게 60px 높이로 뒀다. 일반 명령의 응답을 기다리는 중에도 비상정지는 보낼 수 있다.
설정을 보는 중에도 같은 버튼 규칙으로 비상정지를 보낼 수 있게 했다.
밝은 상태색을 쓰는 다크 모드에서는 버튼 글씨를 어둡게 해 대비를 확보했다.

**휴대폰 첫 화면에는 상태와 조작을 먼저 둔다.** 390px에서 영상 두 개가 먼저 나오면
시작 버튼이 900px 아래로 밀려났다. 지금 상태 → 할 일 → 버튼 → 영상 → 알림 순으로 읽는다.
노트북(1000px 이상)에서는 영상을 왼쪽, 상태·버튼을 오른쪽에 두어 스크롤 없이 한 화면에
들어온다 (`style.css` 맨 아래 미디어 쿼리). HTML 순서는 휴대폰 기준 그대로다.

**명령을 보낸 것과 실제로 멈춘 것을 구별한다.** 일시정지 요청은 별도의 안내로 유지하고,
`paused`를 받은 뒤에만 멈췄다고 안내한다. 비상정지 후 재시작에는 주변 확인 창을 띄우고,
물건 놓기 확인은 팔은 그대로 있고 손만 열려 물건이 떨어진다는 점을 설명한다.
요청이 거부되거나 확인이 늦어지는 안내도 다음 상태 확인으로 지워 버리지 않는다.

**연결을 모르면 대기나 정리 중이라고 표시하지 않는다.** 첫 상태를 받기 전에는 버튼을 잠근다.
연결이 끊기면 숫자를 ‘—’로 바꾸고 단계와 인식 박스를 지우며, 영상 연결을 놓아준다.
상태를 두 번 연속 받은 뒤 영상을 다시 연결한다. 영상만 실패한 경우에도 영상 자리에
다시 연결하는 중이라고 표시한다. 상태 확인 요청은 겹쳐 보내지 않는다.
반대로 끊김 판정도 상태 확인이 **두 번 연속** 실패해야 내린다. 와이파이가 잠깐 늦은
한 번 때문에 영상을 끊었다 붙였다 하며 빨간 배너가 깜빡이지 않게 하기 위해서다
(명령 전송이 실패한 경우는 바로 끊김으로 본다).

**결과에는 다음 할 일을 같이 둔다.** ‘직접 정리’는 로봇이 남겨 둔 물건 수다.
끝났을 때 실패가 있으면 직접 정리하라는 문장을 결과 바로 아래에 남긴다.
중지 뒤 남아 있는 숫자는 이전 정리의 결과라고 표시한다.

**오류는 최근 8개 밖으로 밀려도 찾을 수 있다.** 받은 주의·오류를 별도 펼침 영역에 보존하고
오류 우선으로 표시한다. 이전 알림도 포함한다는 문구로 현재 위험과 혼동하지 않게 했다.
일반 알림도 전체 보기로 열 수 있다. 서버가 보내 준 범위만 보여 주며, 영구 기록은 아니다.
알림 내용이 바뀔 때만 목록을 갱신해 읽던 스크롤 위치를 유지한다.

**설정의 저장 상태를 분리한다.** 읽기 전·연결 끊김·정리 중·일시정지 중에는 잠그고 각각
이유를 알려 준다. 저장 중에는 중복 저장을 막고, 저장값을 다시 읽은 뒤 완료를 표시한다.
다시 수정하면 미저장 안내로 바뀌며, ‘정리 화면’으로 나갈 때 미저장 변경을 확인한다.
체크박스와 라디오는 작은 표시 주변의 라벨 전체가 52px 이상의 누르는 영역이다.

## 서버에 부탁할 것 (A와 상의 필요)

화면을 만들고 실제 사용 흐름을 확인하면서 서버 쪽을 고쳐야 풀리는 문제가 나왔다. 서로의 파일은 고치지 않기로 했으니
여기 적어 둔다.

### 1. 사진 한 장 주소가 있으면 좋겠다 — `GET /api/frame/{cam}` (JPEG 한 장)

지금 `/video/{cam}`은 끝나지 않는 응답이라 연결을 계속 붙잡는다. 브라우저는 한 주소에
동시에 6개까지만 연결하는데, 영상 2개가 자리를 먹은 상태에서 창을 여러 개 띄우면
`/api/status`가 보낼 자리가 없어 **화면 전체가 멈춘 것처럼 보인다.** 실제로 같은 화면을
3개 띄워 재현했고, 세 창 모두 "연결 끊김"이 됐다.

**가이드 9장의 안드로이드 크롬 `ERR_TOO_MANY_RETRIES`도 같은 원인일 가능성이 높다.**
삼성 인터넷에서 됐다는 것도 브라우저마다 연결 수를 다루는 방식이 다르기 때문으로 보인다.

그리고 **이미 이 저장소에 같은 방식의 해결책이 있다.** `dev/scripts/demo_map.py`에
이렇게 적혀 있다.

> 연속 스트림(MJPEG)은 끊기면 화면이 검게 변해서, 사진을 한 장씩 받아 다 받은 뒤에만 바꿈
> → 실패해도 마지막 화면 유지

서버는 `/f.jpg`로 JPEG 한 장을 주고, 화면은 이렇게 받아간다 (`demo_map.py` 26~33줄).

```js
function tick() {
  const i = new Image();
  i.onload = () => { v.src = i.src; setTimeout(tick, 100); };  // 다 받은 뒤에 바꾼다
  i.onerror = () => setTimeout(tick, 500);
  i.src = "/f.jpg?" + Date.now();
}
```

`server.py`에도 같은 걸 `/api/frame/{cam}`으로 넣어 주면, 화면 쪽은 이 패턴을 그대로 쓰겠다.

화면 쪽에서는 일단 이렇게 막아 뒀다.
- 연결이 끊긴 것 같으면 영상을 먼저 놓아준다 → 상태 확인이 다시 통한다 → 통하면 영상을 다시 붙인다
- 화면을 보고 있지 않으면(다른 앱·다른 탭) 영상을 끊는다 → 연결과 휴대폰 배터리를 아낀다

다만 이건 증상을 줄이는 것뿐이다. `/api/frame/{cam}`이 있으면 화면이 영상을 **필요할 때
한 장씩** 받아올 수 있어서 연결을 붙잡지 않는다. 움직임이 중요한 순간에만 `/video/`를 쓰고
평소에는 사진으로 두는 것도 가능하다.

### 2. `cleaner.py`의 `_show_still`에서 박스·글씨 그리는 부분을 빼 주면 좋겠다

화면이 직접 박스를 그리므로 지금은 `detecting` 동안 **같은 박스가 두 번 겹쳐 보인다**
(서버가 구운 영어 라벨 + 화면이 그린 한글 라벨). 서버는 영상만 보내 주면 된다.

빼기 어렵다면 그대로 둬도 동작은 한다. 겹쳐 보일 뿐이다.

### 3. `/api/status`에 화면 크기를 같이 주면 좋겠다

`detected`의 `box`는 픽셀 좌표인데 기준 크기가 어디에도 없다. 지금은 ui_pack 영상이
640×480이라 `app.js`에 그 숫자를 적어 뒀다(`FRAME_W`, `FRAME_H`).

**9주차에 진짜 head 카메라 해상도가 640×480이 아니면 박스가 통째로 어긋난다.**
`"frame": {"w": 640, "h": 480}` 정도를 `status`에 넣어 주면 화면이 알아서 맞춘다.
가이드 7장에 "`status()`에 필드를 추가하는 건 괜찮다"고 되어 있어 적어 둔다.

### (작은 것) 중지·비상정지 뒤에 `detected`가 남는다

`_finish_stop`에서 `current`는 지우는데 `detected`는 남아 있다. 화면 쪽에서 안 그리도록
막아 뒀으니 급하지는 않지만, 서버도 같이 비우는 게 맞아 보인다.

### 4. 대기·완료 상태에서도 비상정지를 상태에 반영해 주세요

가이드 표에서는 `idle`·`done`에도 비상정지가 가능하다. 실제로 대기에서 눌렀을 때
`POST /api/estop`은 `ok: true`였지만 상태는 `idle`로 남았다. 현재 FakeCleaner는
실행 중인 정리 루프가 명령을 처리해야 `estop`이 된다. 종료된 루프에서도 처리되도록
서버 담당 수정이 필요하다. 화면은 버튼 표를 유지하며, 성공 응답만으로 ‘멈췄다’고
꾸미지 않고 일정 시간 뒤 ‘요청은 보냈지만 바뀐 상태를 확인하지 못했다’고 안내한다.

### 5. 대기 중인 명령과 이번 정리의 식별자를 상태에 추가해 주세요

일시정지 요청 문구가 다음 단계 문구에 덮인다. 같은 화면에서는 요청 안내를 유지했지만,
새로고침하거나 다른 휴대폰에서 들어오면 `state: cleaning`만으로는 일시정지 요청이
대기 중인지 알 수 없다. `pending_command`와 명령 처리 결과, 정리 식별자 같은 필드를
추가하면 화면을 다시 열어도 안내를 일치시킬 수 있다. 실패 물건의 목록도 이번 정리
결과에 구조화해서 주면 이전 알림에서 추측하지 않고 정확히 안내할 수 있다.

### 6. 영상의 마지막 촬영 시각도 알려 주세요

영상 주소 자체의 실패는 감지하고 다시 연결하지만, 연결된 채 같은 프레임만 계속
보내는 경우는 `<img>`만으로 판별할 수 없다. 카메라별 마지막 촬영 시각·정상 여부를
상태에 추가해 주면 멈춘 영상을 현재 영상처럼 보여 주는 경우까지 구분할 수 있다.
