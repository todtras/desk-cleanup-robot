# 책상 정리 로봇 — 실제 사용과 UX 수정 기록

## 가장 큰 문제 3개

1. **연결이 끊겨도 옛 상태가 현재처럼 보였다 — 높음.** 실제 서버를 끈 뒤에도 ‘정리 중 / 집는 중’, 이전 숫자와 인식 박스가 남았다. 지금은 ‘상태 확인 불가’, 숫자 ‘—’, 영상·박스 숨김, 조작 잠금으로 바뀐다. 서버를 다시 켜면 상태와 두 영상이 자동으로 복구되는 것까지 확인했다.
2. **휴대폰에서 시작·일시정지 버튼을 찾으려면 먼저 영상을 지나쳐야 했다 — 높음.** 390px 화면의 시작 버튼 위쪽이 문서 기준 약 944px에 있었다. 상태와 조작을 영상 위로 옮겨 약 411px에서 보이게 했다. 비상정지는 계속 아래에 고정하고 설정 화면에도 같은 규칙으로 제공한다.
3. **일시정지를 눌러도 아직 움직이는 이유를 놓치기 쉬웠다 — 높음.** 요청 안내가 다음 단계 문구에 덮였다. 요청과 확인된 상태를 분리해 ‘지금 물건까지 정리하고 멈춤 / 아직 움직임’을 유지한다. 일반 요청의 응답을 기다리는 중에도 비상정지를 보낼 수 있다.

## 확인 방법과 범위

- 2026-11-07, `JEuichan/astra-ux`에서 작업 지시서 전체를 먼저 읽고, 가이드 → 기존 README → HTML/CSS/JS 순으로 읽었다.
- 브라우저 조작은 모두 **Orca 내장 브라우저의 `orca ... --json`**으로 했다. 이동·클릭 뒤 snapshot을 다시 받았다. 일부 `orca click`은 성공 응답 뒤 화면 변화가 없어, 같은 내장 브라우저의 `orca eval`로 실제 DOM 버튼의 `.click()`을 실행하고 상태 변화를 확인했다. 직접 API 호출로 버튼 흐름을 대신하지 않았다. 저장값 확인용 GET은 별도로 사용했다.
- 실제 FakeCleaner, 제공된 녹화 영상, **127.0.0.1:8001**만 사용했다. 8000번 서버에는 조작·종료 명령을 보내지 않았다. 서버·로봇 소스는 수정하지 않았다.
- 390×760 iframe, 기본 브라우저 폭 약 881px, 1280×900 iframe을 확인했다. 1280px 화면은 캡처 안에 들어오도록 바깥에서 축소했지만 내부의 실제 레이아웃 폭은 1280px이다. 실제 휴대폰의 손가락 조작·노치·와이파이는 검증하지 않았다.
- 정상 흐름은 실제 서버로 실행했다. 연결 중 1.8초 지연, 오류 뒤 일반 알림 12개, 실패 1개 완료 결과, 오류 상태의 버튼 표는 **임시 페이지에서 브라우저 응답만 조절한 보조 검증**이다. 이를 실제 로봇 결과로 세지 않았다. 검증용 `_phone.html`, `_wide.html`, `_connecting.html`, `_fixture.html`은 모두 삭제했다.
- 스크린샷은 모두 `/tmp/astra-ux/`에 있다. 조작·snapshot·치수의 원본 기록은 `/tmp/astra-ux/browser-log.jsonl`에 남겼다. 이미지와 검증 기록을 저장소에 넣지 않았다.
- 문서의 시각은 해당 실행에서 받은 서버 알림 시각이다.

## 1. 처음 열었을 때

**(a) 실제 조작:** 메인을 열어 영상이 나오기 전과 후를 봤다. 임시 페이지에서 상태 응답을 1.8초 늦춰 ‘연결 중’을 관찰했다.

**(b) 사용자 느낌:** 연결 중인데 ‘대기’와 0개가 보여 이미 준비됐다고 생각하기 쉽다. 그 순간 모든 조작 버튼이 켜져 있었다. 영상이 비어 있으면 기다리는 중인지 고장인지 알기 어려웠다.

**(c) 심각도:** 높음.

**(d) 수정:** 첫 응답 전에는 ‘확인 중’과 ‘—’를 표시하고 버튼을 잠갔다. 영상 자리에는 불러오는 중이라는 문장을 둔다. 연결 후에는 주변 확인과 ‘정리 시작’을 첫 화면에서 안내한다.

**고친 뒤:** 같은 지연 조건에서 ‘확인 중’, 숫자 ‘—’, 조작 잠금을 snapshot으로 확인했다. 정상 응답 후 서버 상태에 맞게 버튼이 켜지고 두 영상이 표시됐다. 영상 하나의 주소를 임시로 실패시켰을 때는 그 영상에만 재연결 안내가 떴고, 약 3초 뒤 정상 주소와 640px 영상으로 돌아왔다.

**화면:** `/tmp/astra-ux/before-connecting.png`, `/tmp/astra-ux/after-connecting.png`, `/tmp/astra-ux/after-phone.png`

## 2. 정리 시작 → 지켜보기

**(a) 실제 조작:** ‘정리 시작’을 누르고 물건 찾기 → 집기 → 옮기기 → 돌아가기와 재시도를 관찰했다. 상태·단계·숫자·영상 박스·알림을 함께 읽었다.

**(b) 사용자 느낌:** 단계는 도움이 된다. 다만 ‘테이프을(를)’ 같은 문구가 어색하고, ‘못 했어요’와 ‘남았어요’가 둘 다 책상에 남은 물건처럼 느껴졌다. 영상에 이미 찍힌 영어 박스와 한글 박스가 겹치는 때가 있다.

**(c) 심각도:** 숫자의 의미는 중간, 조사 표현과 박스 중복은 낮음.

**(d) 수정:** ‘정리 완료 / 직접 정리 / 정리할 물건’과 단위 ‘개’를 붙이고 ‘직접 정리’의 뜻을 설명했다. 조사를 자연스럽게 바꿨다. 단계·시도 표시와 한글 박스는 유지하되 찾기·집기 및 정상 영상일 때만 박스를 그린다. 영상에 구워진 영어 박스 제거는 서버 담당 범위라 기존 요청을 유지했다.

**고친 뒤:** 실제 실행에서 ‘살펴보는 중 / 집는 중 / 옮기는 중 / 돌아가는 중’을 확인했다. ‘펜 66%’, ‘종이 85%’ 같은 한글 박스와 개수가 표시됐고, 비상정지와 연결 끊김에서는 박스가 없어졌다. 1280px에서도 박스와 영상이 함께 맞춰졌다.

**화면:** `/tmp/astra-ux/before-cleaning.png`, `/tmp/astra-ux/after-1280.png`

## 3. 일시정지 → 계속 → 중지

**(a) 실제 조작:** 정리 도중 일시정지를 누르고 실제 `paused`가 될 때까지 관찰했다. ‘계속’으로 이어서 움직인 뒤 ‘중지’를 눌렀다. 수정 전·후 같은 순서로 실행했다.

**(b) 사용자 느낌:** 일시정지 직후 단계 문구가 바뀌면 요청이 취소됐는지, 이미 멈춘 것인지 불확실하다. 중지 뒤 남은 숫자도 새 정리의 숫자인지 이전 결과인지 헷갈렸다.

**(c) 심각도:** 높음.

**(d) 수정:** 누른 직후 별도 요청 안내를 표시한다. 일시정지는 현재 물건을 마칠 때까지 움직인다고 계속 알리고 `paused`가 와야 멈췄다고 쓴다. ‘계속 / 중지’의 다음 행동을 설명하고, 중지 후 숫자에는 이전 결과라는 문구를 붙인다. 늦게 도착한 이전 명령 응답이 새 비상정지 안내를 덮지 않게 했다.

**고친 뒤:** 돌아가는 단계에서도 일시정지 요청 안내가 유지됐고, 실제 일시정지에서 ‘지금은 멈춰 있어요’로 바뀌었다. 계속 → 중지 후 `idle`, 1개 완료·0개 직접 정리·4개 남음과 ‘중지하기 전의 결과’를 확인했다. 추가로 실제 pause 응답만 브라우저에서 2초 늦췄을 때 일반 버튼은 잠겼지만 비상정지는 켜져 있었고, 이를 눌러 실제 `estop`이 됐다. 늦은 pause 응답 뒤에도 상태가 되돌아가지 않았다.

**화면:** `/tmp/astra-ux/before-pause.png`, `/tmp/astra-ux/after-pause-request.png`

## 4. 비상정지 → 물건 놓기 → 다시 시작

**(a) 실제 조작:** 움직이는 중 비상정지를 눌렀다. 물건 놓기 확인창을 취소한 뒤 다시 열어 실행했다. 수정 후에는 재시작 확인도 취소·실행해 봤다. 설정 화면의 비상정지도 실제 정리 도중 실행했다.

**(b) 사용자 느낌:** 아래에 고정된 큰 버튼은 찾기 쉽다. 그러나 놓기 뒤 바로 움직여도 되는지, 팔이 움직이는지 손만 열리는지 더 명확한 안내가 필요했다. 대기 중 비상정지를 눌렀을 때 서버가 성공 응답을 주고도 상태가 바뀌지 않는 문제도 발견했다.

**(c) 심각도:** 높음.

**(d) 수정:** 확인 없이 보내는 비상정지와 60px 버튼을 유지했다. 멈춘 자세, 물건 낙하, 아래쪽 확인을 쉬운 말로 설명하고 놓기 후에도 비상정지 유지라고 안내한다. 재시작에는 주변 확인을 추가했다. 상태 표는 그대로다. 대기·완료의 비상정지 미반영은 서버 요청 4번에 추가했으며 화면에서 멈춤을 꾸며내지 않는다.

**고친 뒤:** 정리 중 비상정지 → 놓기 취소 → 놓기 실행 후에도 `estop`이 유지됐다. 재시작 취소에서는 움직이지 않았고, 확인 후 실제 정리가 시작됐다. 설정 화면에서도 요청 안내 후 ‘비상정지됨’과 비활성 버튼을 확인했다. 390px의 놓기 확인창에서 문장·버튼이 화면 안에 들어왔고 취소에 초기 초점이 갔다.

**화면:** `/tmp/astra-ux/after-estop.png`, `/tmp/astra-ux/after-release.png`

## 5. 정리 끝까지

**(a) 실제 조작:** 수정 전 18:27:19 시작 → 18:28:43 완료까지 기다렸다. 결과는 4개 정리·1개 실패였다. 수정 후 18:35:06 시작 → 18:36:02 완료까지 다시 기다렸고 결과는 5개 정리·0개 실패였다.

**(b) 사용자 느낌:** 기존에도 끝났다는 문장은 있었으나 실패 뒤 내가 할 일이 결과 옆에 없다. 실패 물건을 알려면 알림을 거슬러 읽어야 했다.

**(c) 심각도:** 중간.

**(d) 수정:** ‘정리를 마쳤어요’를 결과 제목으로 고정하고 전체 개수·완료 개수·직접 정리할 개수를 함께 보여 준다. 실패가 있으면 직접 정리하라는 문장을 바로 아래에 둔다. 정확한 실패 물건 목록은 서버가 구조화해서 주지 않으므로 추측해서 쓰지 않는다.

**고친 뒤:** 실제 완주에서 완료 제목, 5·0·0개, 100%, 책상 확인 안내가 함께 보였다. 실패 분기는 최초 실제 결과와 같은 4·1·0 응답을 임시 페이지에 넣어 추가 확인했다. ‘1개는 로봇이 정리하지 못했어요. 남겨 둔 물건을 직접 정리해 주세요’가 결과 바로 아래에 표시됐다. 이 실패 화면은 보조 검증이며 수정 후 실제 실패 완주는 아니다.

**화면:** `/tmp/astra-ux/before-done.png`, `/tmp/astra-ux/after-done.png`, `/tmp/astra-ux/after-done-failed.png`

## 6. 설정 화면

**(a) 실제 조작:** 테이프를 끄고 속도를 느리게, 다시 시도를 2번으로 바꿔 저장했다. 새로고침한 뒤 값이 유지되는지 봤다. 실제 정리 도중 설정으로 들어갔다. 저장 후 다시 수정하고 ‘정리 화면’으로 나가기를 눌렀다.

**(b) 사용자 느낌:** 기존에는 저장 후 값을 다시 바꿔도 ‘저장했어요’가 남아서 현재 값이 저장됐다고 믿기 쉽다. 설정을 못 바꾸는 이유와 어떻게 풀어야 하는지를 더 분명히 알고 싶었다. 돌아가기 링크도 다른 버튼보다 작았다.

**(c) 심각도:** 중간. 읽기 전·연결 끊김에서 잘못 저장할 가능성은 높음.

**(d) 수정:** 읽기 전 / 저장 중 / 저장 완료 / 미저장을 구분한다. 실제 저장값을 다시 읽은 후에만 완료를 알린다. 잠금 사유를 상태별로 설명하고, 중지하면 수정 가능하다고 안내한다. 미저장 상태에서 ‘정리 화면’으로 나갈 때 확인한다. 링크 44px, 선택 라벨과 저장 버튼 52px 이상을 확보했다.

**고친 뒤:** 테이프 끔·느리게·2번이 저장 및 새로고침 뒤 유지됐고 서버 GET에서도 같은 값이었다. 다시 테이프를 켜자 미저장 안내로 바뀌었다. 나가기 확인창의 ‘계속 수정’으로 변경값이 남는 것을 확인했다. 실제 정리 중에는 모든 입력·저장이 잠기고 이유가 보였으며 비상정지는 사용 가능했다. 처음 값인 모든 물건 켬·보통·1번으로 복원해 저장했다. 이어 모든 물건을 끄고 저장했을 때 선택 안내가 나오는 것, 미저장 변경을 버리고 나왔을 때 서버의 원래 설정이 유지되는 것까지 확인했다.

**화면:** `/tmp/astra-ux/after-settings-locked.png`, `/tmp/astra-ux/after-settings-save.png`, `/tmp/astra-ux/after-unsaved.png`

## 7. 연결 끊김과 복구

**(a) 실제 조작:** 수정 전·후 각각 정리 도중 내가 띄운 8001 서버 프로세스만 종료하고 같은 포트로 다시 띄웠다. 화면은 새로고침하지 않았다. 직접 PID `kill`은 환경 권한에 막혀, 해당 PID를 실행한 도구 세션의 Ctrl-C로 정확히 그 서버만 종료했다. 전체 프로세스 이름으로 종료하지 않았다.

**(b) 사용자 느낌:** 기존 화면은 연결 끊김 경고 옆에 ‘정리 중 / 집는 중 / 2번째’와 물병 인식 박스를 남겼다. 로봇이 현재 무엇을 하는지 오해할 수 있다.

**(c) 심각도:** 높음.

**(d) 수정:** 현재 상태 확인 불가를 본문에도 표시한다. 숫자·진행 정보·단계·박스·이전 영상을 지우고, 비상정지를 포함해 전달할 수 없는 버튼을 잠근다. 남겨 둔 알림은 끊기기 전 내용임을 명시한다. 정상 상태를 연속 두 번 받으면 영상을 다시 붙이는 동작을 유지했다.

**고친 뒤:** 실제 종료 직후 상태 ‘확인 불가’, 6개 명령 모두 비활성, 이미지 `src` 둘 다 없음, 인식 박스 0개를 확인했다. 다시 띄우자 ‘연결됨 / 대기’와 실제 서버의 최신 숫자, 두 영상의 정상 주소·너비 640px가 자동 복구됐다. 서버가 재시작되어 대기가 된 것이며, 연결이 끊긴 순간 로봇이 멈췄다고 주장하지 않는다.

## 8. 390px·넓은 화면·다크 모드

**(a) 실제 조작:** 390×760 iframe에서 첫 화면과 설정·놓기 확인창을 사용했다. 기본 폭 약 881px와 1280×900 iframe도 봤다. 내장 브라우저의 실제 다크 모드를 확인하고, 기존 `data-theme` 선택자로 밝은 모드도 표시했다.

**(b) 사용자 느낌:** 기존 390px에서는 영상 두 개만 먼저 보여 조작을 찾기 어렵다. 밝은 초록·빨강 위의 흰 글씨는 다크 모드에서 흐릿하다.

**(c) 심각도:** 조작 위치는 높음, 글씨 대비는 중간.

**(d) 수정:** 상태 → 조작 → 영상 → 알림 순서로 옮겼다. 넓은 화면에서는 상태와 조작을 나란히 둔다. 중요한 설명을 14px 이상으로 맞추고, 다크 모드의 밝은 버튼에는 어두운 글씨를 쓴다. 밝은 모드의 상태 글씨도 진하게 조정했다.

**고친 뒤:** 390px에서 시작 버튼의 위쪽이 약 944px → 411px로 올라왔다. `scrollWidth === innerWidth`를 390px와 1280px에서 확인했다. 큰 화면에서 두 영상과 한글 박스를 함께 봤다. 계산된 색의 대비는 시작 버튼 밝음 7.13:1·어두움 8.54:1, 비상정지 밝음 5.62:1·어두움 6.63:1, 상태 배지 최저 4.84:1이었다. 비활성 버튼의 투명도는 이 수치에 포함하지 않았다. 실제 한 손 엄지 도달성은 기기 검증이 남았다.

## 9. 손가락 크기와 초점

**(a) 실제 조작:** 메인·설정·놓기 확인창을 열어 버튼과 선택 라벨을 누르고 `getBoundingClientRect()`로 실제 크기를 측정했다.

**(b) 사용자 느낌:** 기존 일반 버튼과 비상정지는 충분히 크지만, 설정/돌아가기 링크는 약 39.6px로 작다. 체크 표시 자체보다 라벨 전체를 누를 수 있는지가 중요하다.

**(c) 심각도:** 중간.

**(d) 수정:** 링크 최소 44×44px, 일반 버튼 52px, 비상정지·물건 놓기 60px, 선택 라벨 52px를 유지·확보했다. 키보드 초점 테두리를 분명하게 하고 확인창에서는 취소에 먼저 초점을 준다.

## 10. 알림이 10개 넘게 쌓일 때

**(a) 실제 조작:** 실제 시작·중지·비상정지·재시도로 알림을 10개 이상 쌓아 읽었다. 이어서 오래된 오류 1개 뒤 일반 알림 12개를 넣은 조건을 수정 전·후 브라우저에서 비교했다. 수정 후 전체 보기·주의/오류 펼치기·목록 스크롤을 사용했다.

**고친 뒤:** 실제 알림 11개에서도 최근 8개·전체 보기·중요 알림이 표시됐다. 고정 13개 조건에서는 기본 목록이 8개여도 오래된 오류 1개가 별도 미리보기와 펼침 목록에 남았다. 전체 보기 후 일반 목록 13개·중요 목록 1개를 확인했다. 목록을 100px 내린 뒤 다음 상태 확인에도 100px가 유지됐다. 서버가 보낸 최근 최대 50개 밖의 영구 기록은 제공하지 않는다.

## 추가 발견과 남겨 둔 범위

- **대기·완료에서 비상정지 성공 응답과 실제 상태가 다름:** 서버 루프가 종료된 상태에서는 명령이 상태에 반영되지 않는 문제다. 버튼 표를 바꾸거나 프런트에서 `estop`을 가짜로 만들지 않았다. 요청 확인이 늦어지면 확인하지 못했다는 안내를 남긴다.
- **카메라 연결은 살아 있으나 화면이 멎는 경우:** 주소 실패·로딩 실패는 재연결하지만 같은 프레임이 계속 오는지는 현재 API로 구분할 수 없다. 마지막 촬영 시각이 필요하다.
- **다른 기기·새로고침의 일시정지 요청:** 같은 페이지에서는 요청 안내를 유지한다. 다른 화면에서도 일치시키려면 서버의 대기 명령 정보가 필요하다.
- **한글/영어 박스 중복과 좌표 기준 640×480:** 기존 서버 요청을 유지했다. 영상 가공·실제 카메라 해상도 계약을 프런트에서 임의로 바꾸지 않았다.
- **설정의 모든 물건 해제:** 정리할 물건을 하나 이상 선택하도록 저장 전에 안내한다. 새로고침 시 미저장 경고는 브라우저 기본 동작에도 의존하므로 실제 모바일에서 추가 확인이 필요하다.
- **설정과 서버 문구:** 저장 API는 기존 코드·실제 서버에 맞는 `PUT /api/settings`를 유지했다. 서버 문구는 내용과 오류를 숨기지 않고 조사만 읽기 쉽게 보정했다.
- **기록·PIN·실물 로봇:** 이번 사용성 수정 범위에서 새 서버 기능을 만들지 않았다. 실제 하드웨어 비상정지 성능이나 안전을 검증한 결과는 아니다.
- **브라우저 도구의 한계:** 클릭 성공 응답과 실제 동작이 일치하지 않는 경우가 있어 snapshot·DOM·서버 상태로 결과를 확인했다. 임시 페이지 사용 중 도구 연결이 한 차례 멎어 새 Orca 탭으로 이어 갔다. 정상 페이지에서 재검증했다.

## 보존 규칙과 전달 상태

- `app.js`의 `STATES` 선언을 Git HEAD 원본과 비교해 **문자열까지 동일**함을 확인했다.
- 보조 응답으로 여섯 상태의 실제 버튼을 확인했다: 대기/완료는 시작·비상정지, 정리 중은 일시정지·중지·비상정지, 일시정지는 계속·중지·비상정지, 비상정지는 시작·놓기, 오류는 비상정지. 알 수 없는 상태에서는 모두 잠긴다.
- 영상 연결 해제/복구, 놓기 확인창, 한글 인식 박스, 정리 중 설정 잠금을 유지했다. 외부 자원·빌드 도구·프레임워크를 추가하지 않았다.
- `node --check dev/app/static/app.js`와 `git diff --check`로 문법·공백 검사를 수행했다. 최종 정상 페이지의 Orca 콘솔 메시지는 비어 있었다. 실제 브라우저 시나리오 결과는 위에 적었다.
- 수정·추가 파일은 `dev/app/static/` 아래의 HTML 2개, CSS, JS, README와 이 기록뿐이다.
- 이 변경은 `ui/screen` 브랜치의 커밋에 들어 있다. 검토 당시 샌드박스 권한 때문에 Codex가 직접 커밋하지 못해 B가 바깥에서 커밋했다.
